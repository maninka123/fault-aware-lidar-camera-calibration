# V3 generalization and overfitting audit

Date: 6 November 2026. Protocol: [PROTOCOL_GENERALIZATION.md](PROTOCOL_GENERALIZATION.md), frozen at commit `cdb4b22` before the groups were run. Generated tables: [results/generalization_run.md](results/generalization_run.md),
[results/dataset_audit.md](results/dataset_audit.md). Run provenance: [results/generalization_run_provenance.json](results/generalization_run_provenance.json) (source commit `cdb4b22`, frozen sources clean).

## Verdict

**Generalization is not established, and for exact fault attribution there is nothing to generalize.** On eight groups (four used in V2/V3 development, four never used in any V2/V3 experiment or design decision), no method attributes the injected fault group
reliably: improved V3 gets 0 exact attributions of 40 injected changes, original V3 0, V2 2 (one each on two groups), the production policy 0 and the frozen maintenance optimizer 0. What is consistent across groups is detection (improved V3 36/40, original V3 37/40) and
ambiguity (the true group is inside the reported set in most detected cases). The one apparent advantage of the improved front end seen earlier (0 false alarms in 12 no-change trials) **did not hold up**: it false-alarmed on `pair3_oct28`
(a group never used in design) on 1 of 1 nominal trial and 1 of 2 nuisance trials, where the original V3 did not; the original V3, V2 and V2 without intensity false-alarmed on `d1_nov5_off` (the deeper, different scene), where improved V3 did not.
Each group contributes one nominal trial, so these are single events, not rates.

This is evidence of consistency and of fragility, not evidence of generalization. All eight groups are the same camera model and the same LiDAR model from one laboratory family.

Findings of the audit:

* **No capture appears in two groups**: content hashes found 0 cross-group duplicates (copies of the same captures in other result folders were collapsed to one group).
* **The four Oct 28 devices are one scene, not four.** `pair_1`'s median image shares 28 to 34 homography inliers with each of the other three, and the other three share 11 to 23 among themselves; every pair of groups from different sessions or devices outside this set shares 0 to 10. Sep 29 on and off share 80 (one scene). Only the Nov 5 groups are a different scene, with a deeper range
  (p95 9.6 to 9.7 m against 5.6 to 6.3 m elsewhere). Nov 5 off and on share almost nothing with each other (0 inliers) but are one device, one day.
* **Independent units are few:** about three scenes (Sep 29, Oct 28, Nov 5), three sessions, five device identities (pair_1 recurs on Nov 5), and one camera model and one LiDAR model throughout. Captures within a group are one static scene; perturbations of a group are perturbations of that scene; neither count as independent.
* **Reference calibrations:** each device uses its own board-based calibration; the Nov 5 groups use the Oct 28 device-1 calibration (the file their own application checks used). The anchor of every group is built from that group's own captures only and is never reused across groups; the registry check rejects one reference shared by different devices.
* **Excluded:** `creep_three` and the two 4-capture Nov 5 board groups (below the cross-validation floor).
* **Not covered by any data:** a different LiDAR model or scanning pattern, a different camera family, lighting, reflective-surface or occlusion conditions chosen on purpose, nuisance-only physical sessions, physical faults. The image descriptors in the audit (brightness, saturation, edge density, range, angular spread) differ little between groups, so
  feature distributions are similar except depth range.

## 2. Framework (what was built)

* `research_calibration/fault_diagnostics_v3/generalization.py`: registry validation (overlapping captures, shared references across devices, mislabelled prior use), leave-one-scene/session/device/group-out folds with a leakage assertion, anchor-provenance check, a `TrialInput`/`TrialTruth`
  split so methods see only a calibration and captures, a frozen-configuration guard, per-group metrics, worst-group and gap, and leave-one-out variant selection.
* `tools/audit_datasets_v3.py`, `tools/run_generalization_v3.py` (freeze and run; refuses to start if frozen constants or sources changed), `tools/summarize_generalization_v3.py`.
* **A separate pipeline for genuinely new data**: `research_calibration/fault_diagnostics_v3/unseen.py` and `tools/unseen_pipeline_v3.py` (`register`, `freeze`, `run`). A new group is admitted only with no prior use, no capture matching a known group, a declared camera, LiDAR and scan pattern, and a measured scene-novelty verdict; the run requires a *committed* freeze of the group list and
  fingerprints plus the unchanged development freeze. **No unseen data exist today; the pipeline has been exercised only on synthetic registries.**
* **Tests that fail on leakage:** 36 tests across `test_generalization_v3.py` and `test_unseen_v3.py` cover overlapping capture groups (by content and by name), reused calibration anchors across devices, mislabelled prior use, anchors built from foreign captures, folds that train on the held-out scene, device or session, a held-out group that
  shares a capture, selection that reads a held-out group (guard object raises), methods receiving truth fields, pairing front ends given an anchor, a frozen constant or source edited after the freeze (including the real frozen file), line-ending-stable hashing, and the unseen-data admission and freeze rules.

## 3. Protocol, deviations and amendments (nothing hidden)

* Conditions were reduced at the user's request for speed: one replicate; nominal, five injected changes (rotation 1 degree, translation 6 cm, principal point 3 px, focal length 2 %, rotation plus translation); two nuisances for the improved variants only. The omitted conditions are the smaller magnitudes, so detection here is easier than in earlier studies.
* The frozen sources were edited **after** the run, and the freeze was refreshed (original freeze preserved at `cdb4b22`). The edits are reporting and guard code and change no computed result: (1) the summarizer read the original-optimizer decision under the wrong key (`production` instead of `legacy_optimizer`) and crashed; (2) it
  stored the headline method under only one name, which made the nuisance table print a **false zero** for it, left the recovery column empty and the leave-one-out table empty (found by reading the output); (3) guard clauses for empty inputs, a missing held-out group, a registry group with missing fields and a selection without training groups. All tables below were regenerated from the unchanged trial files.
* Constants were fixed on the development groups before these groups were run. The four not-used groups were seen by the desktop application's own checks, and one Nov 5 overlay was inspected by eye while fixing an application figure; no V2/V3 experiment or design choice used them. They are **not blind data**.
* The "original method" is the frozen maintenance optimizer inside the common protocol, not the full maintenance application (minutes per trial).

### Worst group and generalization gaps

* **False alarms:** the worst groups are `pair3_oct28` for improved V3 (1/1), `d1_nov5_off` for original V3, V2 and V2 without intensity (1/1), `pair4_oct28` for the production policy (1/1). The mean over not-used groups (0.25 for improved V3, 0.25 for original V3) is above the mean over development groups (0 for both): the false alarms happened on groups not used in design, but with one nominal trial each the difference is one event.
* **Detection:** worst group for improved V3 is `d1_nov5_on` (3/5; original V3 4/5); for original V3 `rig_sep29_off` (3/5).
* **Exact attribution:** worst for every method is a group with 0/5; there is no generalization gap in exact attribution because the development mean is also 0.
* **Nuisance-only trials** (spurious lines, ghost edges, improved-V3 variants): the headline `geometric` front end alarmed on 1 of 16, on `pair3_oct28`; the existing oriented pairing alarmed on 8 of 16; removing the confidence weighting alarmed on 6 of 16; removing balancing on 5 of 16; removing the visibility test on 0 of 16.
* **Calibration recovery** (median projection error versus the anchor, alarmed drift trials): the headline front end reduces the error on 7 of 8 groups (for example 3.00 to 2.31 px, 2.64 to 1.76 px) and leaves it unchanged on `rig_sep29_off` (1.70 to 1.73 px). The reductions are modest and no group reaches the sub-pixel recovery of the correct-pair control seen earlier.
* **Leave-one-out selection of the pairing variant** (training groups only): the selected variant changed between folds (no-visibility in 6 of 12 folds, the default in the other 6). In the six folds where it chose something other than the default, it was worse than the default by the declared cost every time (for example the rig scene: 2 wrong labels against 1; `d1_nov5_on`: 2/5 detections against 3/5) and never better. The best variant in hindsight differs in nearly every fold. No variant is robustly best.

## 6. Interpretation

* The earlier gain of the improved front end came from reducing false alarms and wrong labels; across eight groups it reduces wrong labels (1 against 1 for original V3, 11 for the production policy, 13 for the frozen optimizer, 3 for V2) but not false alarms, and loses a detection on `d1_nov5_on`. **It is not shown to generalize better than the original V3.**
* Valid geometry is what the method uses (signed residuals, fisheye Jacobians, explicit ambiguity), and that is why its detections and ambiguity sets are consistent across groups. But its attribution needs correct correspondences (root-cause analysis: 17 of 28 exact with correct pairs, 1 of 28 with the best automatic pairing), and
  the front end's evidence quality does vary by scene (it false-alarmed on one same-scene device and not on the deeper new scene). The audit finds no sign that the method learned the recorded scenes (its constants were fixed before these groups and no group-specific choice exists), but also no sign that it would hold on a scene that differs in kind.
* Exact attribution fails in the same way on all eight groups, including the Nov 5 scene with a different depth distribution; the cause is correspondence quality, not scene memorization.

## 7. Datasets needed (to establish generalization)

1. **Independent scenes**, at least ten, chosen on purpose: low and high texture, wide depth variation (indoor and outdoor), strong and low illumination, reflective surfaces and windows, partial occlusion, moving objects. Each with its own session; no two groups sharing a room layout.
2. **Other sensor configurations**: another LiDAR model and scan pattern (repetitive scanning as well as the Livox rosette), another camera family and field of view, different baselines and mounting angles. Declare them at registration (`unseen_pipeline_v3.py register`).
3. **Independently measured faults**: jig- or tracker-measured mount rotations and translations and a controlled intrinsic change, several magnitudes, repeated across sessions; plus nuisance-only sessions (wet or dirty window, low light, occlusion, a known timestamp offset).
4. **Correspondence ground truth** for part of a scene (fiducials or targets placed in natural sessions), since attribution depends on pairing identity.
5. **Simulated data** with exact poses, depth, visibility and five LiDAR profiles from the separate simulator project (adapter exists), with scene-level splits and labels withheld from every choice.
6. Several nominal sessions per device to measure false-alarm rate per session (here one nominal trial per group).

## 8. How to run it on new data

```text
python -B tools/unseen_pipeline_v3.py register --id NEW --device DEV --session YYYY-MM-DD --state "..." --data-dir STACKED_NPZ --reference REFERENCE.json --camera-model M --lidar-model L --scan-pattern P
python -B tools/unseen_pipeline_v3.py freeze     # then COMMIT docs/research/v3/FROZEN_UNSEEN.json
python -B tools/unseen_pipeline_v3.py run research_artifacts/NEW_FOLDER
python -B tools/summarize_generalization_v3.py research_artifacts/NEW_FOLDER
```

The run fails if the development constants or sources changed, if the unseen freeze is not committed and clean, or if the groups or capture fingerprints differ from the freeze. Do not inspect outcomes before freezing; a change after seeing results is a new development round.

## 9. Corner cases found and fixed in this pass

* The overlay card crashed on a capture with no or one LiDAR point (the distance scale needs points): it now says so; tests added.
* The summarizer false zero, empty tables and wrong key described in section 3.
* Empty or missing inputs: variant selection without training groups or variants, a gap computed on no groups or for a missing held-out group, a registry group missing required fields, registering a new group from an empty folder or missing reference, a summary with no common trials.
